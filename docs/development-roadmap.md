# 开发计划

本文是前端阶段划分、任务拆分和验收标准的唯一来源；完成情况记录在[开发进度](progress.md)。后端阶段见[后端开发计划](https://github.com/Mingan-X/Resume-Studio-Backend/blob/master/docs/development-roadmap.md)。未标记为“已完成”的内容都不是已交付能力。

| F1.2 | 应用骨架与共享层 | 布局、路由、HTTP客户端、错误标准化、全局错误处理、设计变量、404页 | 无 | — | 待验收 |
| F1.3 | 契约接入与任务页 | OpenAPI快照与类型生成、任务进度页与取消 | S1.4（T8、T9） | — | 待验收 |

状态只使用：未开始、进行中、待联调、待验收、已完成、已搁置。“待联调”表示基于MSW完成、尚未与真实后端验证。状态变化必须同时更新本表和[开发进度](progress.md)。

F1.1与F1.2不依赖后端业务接口，可以立即开始。F2.x可以在后端对应接口的Schema合并进契约后，先基于MSW开发到“待联调”。

## 2. 任务规范

2026-11-27起，按维护者要求，F1.1至F3.2全部拆分到任务级（见§6）。每个阶段开始时仍须对照当时的代码、后端已合并契约和已确认决策复核该阶段任务；需要调整编号、依赖、产出或验收时，先在progress记录原因并请维护者确认。

每个任务写明编号（`<阶段>-T<序号>`）、目标、依赖、产出、验收和检查命令。

任务完成的定义（Definition of Done）：

1. 验收条件全部有对应测试或可复核的运行记录。
2. `pnpm run typecheck`、`pnpm run lint`、`pnpm test`、`pnpm run build` 通过；涉及用户流程时 `pnpm run test:e2e` 通过。
3. 遵守[界面规范](ui-guidelines.md)第2节的展示规则与[编码规范](coding-standards.md)。
4. 依赖变化同步提交锁文件，并更新ADR版本表。
5. 在[开发进度](progress.md)追加记录：完成内容、验证命令与结果、未执行项及原因。

### 执行顺序与停止条件（前后端连续执行）

前后端共用一套批次、延后任务表与停止条件，定义见[后端开发计划](https://github.com/Mingan-X/Resume-Studio-Backend/blob/master/docs/development-roadmap.md#执行顺序与停止条件前后端连续执行)。2026-11-27维护者确认全部决策（FD1、FD2见§7），授权AI连续完成F1.1至F3.2，不逐阶段停下等待验收。

前端顺序为 F1.1 → F3.2-T1（CI，提前执行）→ F1.2 → F1.3 → F2.1 → F2.2 → F2.3 → F2.4 → F2.5 → F3.1 → F3.2其余任务。每个F2.x/F3.x阶段在后端对应阶段合并到后端 `develop` 后开始；契约快照取自后端 `develop`，SOURCE.md记录所取提交SHA。前端额外规则：

- 分支：阶段分支从前端 `develop` 创建，完成后 `--no-ff` 合并回 `develop` 并标“待验收”；可推送阶段分支与 `develop`，不得修改 `main`。见[CONTRIBUTING](../CONTRIBUTING.md)。
- 先基于MSW开发，再与本地真实后端冒烟。依赖真实模型产出的冒烟（F2.3-T4、F2.4-T7、F2.5-T4、F3.2-T2）及目标环境部署（F3.2-T6）按后端“统一验收前延后的任务”表处理：先完成其余部分，延后项在progress标明，不阻塞阶段合并。
- 后端未提供某字段时，按[AGENTS](../AGENTS.md)记录问题；该问题使后续任务无法进行时停止等待维护者，否则跳过该部分继续，不手写类型或自行拼装字段。
- 检查失败与必须停止的情况按后端同名规则执行。

**检查简称**：下表中“基础检查”指 `pnpm run typecheck`、`pnpm run lint`、`pnpm test`、`pnpm run build`；“E2E”指 `pnpm run test:e2e` 的MSW流程组；“真实冒烟”指连接本地真实后端的冒烟组（后端未启动时如实记录为未执行）。契约快照更新后另跑契约测试。
